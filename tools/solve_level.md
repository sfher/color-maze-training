# Color Maze 关卡求解器使用教程

工具：`tools/solve_level.py`（Python 3，无第三方依赖）
作用：按游戏运行时的真实规则，精确计算一张关卡地图的**最少通关步数**，并给出可逐键复现的走法。配套"不死亡"与"全程不受伤"两种口径，用于难度标定和有解性检查。

---

## 1. 快速开始

在**仓库根目录**（`Unity项目实训/`）执行：

```bash
# 语义自测（5 个手算用例，改过脚本先跑这个）
python tools/solve_level.py --selftest

# 解一张关卡（默认出生点 = Unity startCell(1,1)，两种口径都算）
python tools/solve_level.py "Color Maze/Assets/Data/Level_06.asset" --mode both
python tools/solve_level.py "Color Maze/Assets/Content/Levels/Level_Water World.asset" --mode both
```

输出三部分：地图摘要（出生/出口/传送门配对/StepLimit）→ 每种口径的**最少步数 + 按键序列 + 终态** → 逐步回放日志（每步的坐标、氧、血、弹药、材料、引信）。

## 2. 坐标与方向约定（重要，踩过坑）

- **资产 `rows[0]` = 屏幕顶部**（文件第一行画在屏幕最上面）。
- Unity 的 `startCell(x, y)` 中 **y 从屏幕底部向上数**，所以求解器内部把它换算成资产行：`行 = 高度-1-y`。`--start` 参数接受的就是这种 Unity 坐标（默认 `1,1` = 左下角附近）。
- 回放日志里的坐标是 **(资产行, 列)**：行号减小 = 屏幕上方，列号增大 = 屏幕右方。
- 按键序列里 `W/A/S/D` = 屏幕上/左/下/右（与游戏内 WASD 一致），`[E]` = 在当前位置放炸弹（不耗步数）。

## 3. 命令行参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `asset` | 水世界 | 关卡 `.asset` 文件路径 |
| `--mode` | `both` | `no-death`（允许受伤但不能死）/ `damage-free`（血恒 3）/ `both` |
| `--start x,y` | `1,1` | Unity 世界坐标出生点（y 自底向上） |
| `--require N` | 读资产 | 出口所需材料数。默认读关卡资产的 `requiredMaterials`（运行时已实装该判定）；临时改口径可传 N 覆盖 |
| `--selftest` | — | 跑 5 个合成关卡自测，应全绿 |
| `--no-verify` | — | 跳过独立回放校验（不建议） |

## 4. 两种口径的用途

- **no-death（不死亡）**：血可以掉但不能归零。求解器会主动利用"吃 1 次自家炸弹爆炸 / 穿岩浆"换步数——这是合法战术，不是 bug。答案 = 这张图的**绝对最少步数**。
- **damage-free（全程不受伤）**：血恒 3。代表"普通玩家理论最优"，比 no-death 慢几步（躲避要走位）。

两者差值本身是有信息量的设计指标：差距大说明地图存在"高风险捷径"。

## 5. 拿到路线后怎么人工验证

1. 进 Unity Play，按按键序列逐键操作（撞墙/撞灰石不耗步，走错了直接 R 重开）。
2. 对照三个东西：**步数 HUD**、**事件点**（回放日志里标了 传送/开箱/拾材料/[E] 的步）、**终态**（血/氧/弹药/材料/金币）。
3. 对不上时记录"第几步 + 现象"（例如"第 5 步传送落点不对"），这比"都对不上"好定位得多。

## 6. 关卡设计工作流建议

改完地图文本（`LevelDefinition.rows`）后立刻跑一次，看四件事：

1. **有没有解**：无解输出 `无解`，常见原因=材料/出口被灰石封死且炸弹不够（每宝箱 1 弹、一弹炸十字四邻）。
2. **最少步数 vs StepLimit**：建议 StepLimit ≈ 无伤最优的 1.5~2.5 倍，留失误空间。
3. **是否必须受伤**：no-death 与 damage-free 步数差、终态血量，判断"高风险捷径"是不是你想要的。
4. **结构性捷径**：出生点紧邻出口行/传送门直通关底的情况，求解器会用极短步数暴露出来（第六关旧版 14 步速通就是被它抓出来的）。
5. **求解时长是「精致度」参考指标之一**：认真设计的关卡（资源抉择多、路线分叉真实）会让求解器也花大力气——Level_06 无伤口径 13 万态 ~1 分钟、Level_07（require 3）59 万态 ~6 分钟，而随手乱点的 Level_08 亚秒级坍缩（5747 态）。使用注意：①只在同一版求解器下比较相对量级（实现优化会改变绝对耗时）；②它测「决策空间规模」而非「好坏」，要配合步数余量/是否强制受伤/人类通关时长一起看；③区分「丰富的慢」与「病态的慢」——传送门连环等设计事故也会慢，那种要改图。

## 7. 维护约定（改规则必须同步）

求解器头部有一张**规则保真表**，每条对应运行时代码（`PlayerGridMover` / `PlayerStats` / `LevelFlowController` / `MazeBootstrapper` / `DelayedBombState`）。**改任何游戏规则（氧气、炸弹引信、传送门、材料需求……）都要同步改脚本**，然后：

```bash
python tools/solve_level.py --selftest   # 必须全绿
```

已知边界（均按运行时真实行为建模）：出生点在墙/灰石里是合法的（出生不检测格子，能走出不能走回）；孤立传送门=踩上原地不动且回 1 氧；爆炸判定先于落格效果（踩门瞬间被传送走可躲炸）。

## 8. 原理一页纸

A* 搜索：动作 = 放炸弹(0 步)/四向移动(1 步)；状态 = (位置, 氧, 血, 材料数, 炸弹数, 已破坏/已收集集合, 引信)。启发函数 = 松弛图（灰石视为可走、忽略氧血）上"位置→最近材料→出口"的距离下界，保证最优；剪枝有三层——**资源支配**（同核心状态下"步数≤且氧≥血≥弹≥破坏⊇"的记录压制次优，把氧/血/炸弹维度压进比较，否则宝箱多的图会状态爆炸跑不完）、无用放弹剪枝（十字内无可破灰石时不准放）、堆内残留支配项跳过。答案路线再由一个**独立实现的回放校验器**逐步断言通过——两套实现互为对账，历史上它抓出过的人算错误比自己出错的次数多。

性能预期：中小图秒级；宝箱 20+ 的图几十秒量级属正常，超过几分钟说明该图的状态空间值得再压缩或拆分设计。
